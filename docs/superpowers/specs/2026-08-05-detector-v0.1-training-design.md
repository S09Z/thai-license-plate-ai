# Detector v0.1 — fine-tune YOLOv8n on ThailLand Plates

## Context

`datasets/` and `models/detector/` are both empty except for `.gitkeep`. Every `/detect` and
`/recognize` call returns `503 Service Unavailable` (`PlateDetector` raises `FileNotFoundError`
when `models/detector/best.pt` is missing — see `app/core/config.py:39`,
`app/services/detection_service.py:20`). This is blocking reality #1 from the project's memory
log: the Phase 7 UI happy path has only ever been demonstrated against a stub server, never a real
model. This spec closes that gap with a first, honestly-measured baseline — not a production-grade
detector.

## Decision

Three approaches were considered:

- **(A) Fine-tune pretrained `yolov8n.pt` on the ThailLand Plates dataset alone — chosen.**
  Fastest path to a real, measured number. Matches how every other phase in this project shipped:
  small, honest, benchmarked, then iterated.
- **(B) Train from scratch — rejected.** Random-init YOLO on ~200 images performs far worse than
  fine-tuning a pretrained backbone. No justification to do this.
- **(C) Merge ThailLand Plates with other public datasets first — deferred.** Would likely improve
  accuracy but adds license-checking and merge/dedup work before any number exists. Revisit once
  v0.1's mAP is measured and judged insufficient.

## Dataset

[ThailLand Plates](https://universe.roboflow.com/thailland-plates/thailand-license-plates) — 200
images, single `license-plate` class (whole-plate bounding boxes on vehicle photos, matching what
`PlateDetector` needs — it treats every YOLO box as a plate with no class filtering), CC BY 4.0,
Roboflow export includes a pre-split `train/valid/test` with YOLO-format labels and a `data.yaml`.

**Caveat, stated up front:** 200 images is thin, and Roboflow's typical split leaves a small
(~20-30 image) validation set. The first mAP number will be noisy and this will very likely
undershoot real-world accuracy. That is an acceptable v0.1 outcome — the goal is replacing an
indefinite `503` with a real, measured baseline, not shipping a production detector.

## Data pipeline

Roboflow requires an account login to download — this is a **manual, one-time step**, not
scripted: download the "YOLOv8" export zip from the dataset page, extract it to
`datasets/raw/thailand-license-plates-v1/`. This directory is already gitignored
(`datasets/raw/` in `.gitignore`) and Roboflow's export is already training-ready (split +
labelled), so no `processed/` or `augmented/` step is needed for v0.1 — extending
`datasets/processed/`/`datasets/augmented/` is out of scope until augmentation is actually needed.

## Training script — `scripts/train_detector.py`

Follows `docs/benchmark/bench_ocr.py`'s conventions: a module docstring stating what it does and
the exact `poetry run python scripts/train_detector.py` invocation, plain `argparse`, named
constants for defaults rather than a separate YAML config system (`configs/` stays empty — nothing
to tune yet justifies that abstraction).

Fine-tunes Ultralytics' COCO-pretrained `yolov8n.pt`:

```python
model = YOLO("yolov8n.pt")
model.train(
    data="datasets/raw/thailand-license-plates-v1/data.yaml",
    epochs=100,        # --epochs override
    batch=16,           # --batch override
    imgsz=640,
    device="cpu",        # matches the confirmed compute target
    patience=20,          # early stop if val loss plateaus
)
```

**Error handling:** if `datasets/raw/thailand-license-plates-v1/data.yaml` does not exist, the
script exits with a clear message telling the user to complete the manual download step above —
not a raw stack trace.

**Output handling:** Ultralytics writes to an incrementing `runs/detect/trainN/` directory. The
script locates the actual output directory from the `train()` result object (not a hardcoded
`runs/detect/train`), then copies `weights/best.pt` to `models/detector/best.pt`.

## Experiment record — `docs/experiments/detector-v0.1.md`

`models/detector/best.pt` is gitignored by design (`.gitignore`: "store release models externally,
not in git"), so this markdown file is the tracked source of truth, satisfying CLAUDE.md's
"track version, dataset, metrics, git commit":

- Dataset: name, version/link, license, image count, split sizes
- Hyperparameters: epochs actually run (may stop early via `patience`), batch, imgsz, optimizer
  and learning rate (Ultralytics' resolved values, not just the requested ones)
- Metrics: `mAP50`, `mAP50-95`, precision, recall, straight from Ultralytics' validation output
- Git commit hash of `scripts/train_detector.py` used for the run
- The noisy-validation-set caveat from the Dataset section above, restated next to the actual
  numbers

Where the `.pt` binary itself gets distributed (GitHub release asset, shared drive, etc.) is
explicitly **not** decided by this spec — out of scope until v0.1's accuracy is judged worth
distributing.

## New benchmark — `docs/benchmark/bench_detect.py`

Phase 1 never got a reproducible latency benchmark because there was never a real model to
benchmark against. Once `models/detector/best.pt` exists, this closes that gap the same way
`bench_ocr.py` did for OCR: measures real detection latency on a real image against the `<25ms`
budget in `CLAUDE.md`, using the shipped `PlateDetector` class directly (not a reimplementation).

## Verification

```bash
make test                                          # unaffected — detector is mocked in tests
poetry run python scripts/train_detector.py        # produces models/detector/best.pt (local, gitignored)
poetry run python docs/benchmark/bench_detect.py   # new, real latency number
poetry run uvicorn app.main:app                    # manual browser pass: upload a real photo,
                                                     # confirm /recognize no longer returns 503
```

## Explicitly out of scope for v0.1

- Approach (C): merging additional public datasets
- Data augmentation pipeline
- Hyperparameter sweeps
- GPU/cloud training paths (compute target confirmed as CPU-only)
- Any model-registry tooling beyond the one experiment markdown file
- New pytest coverage for `scripts/train_detector.py` itself — same reasoning as the existing
  benchmark scripts: it is a manual, evidence-producing run, not unit-testable logic

## Deferred: OCR fine-tuning

A related question came up during this brainstorm (no dedicated Thai-plate-fine-tuned OCR
checkpoint exists publicly; the realistic future path is fine-tuning PaddleOCR's stock Thai
recognizer — already the engine `ocr/recognizer.py` wraps — on real plate crops once they exist).
This is **not part of this spec**. It depends on having real plate crops, which this detector spec
is a prerequisite for, and is expected to become its own spec later.
